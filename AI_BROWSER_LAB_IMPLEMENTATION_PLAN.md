# AI Browser Agent Lab - Implementation Plan

**Project:** Standalone, single-user, local proof of concept

**Code, UI, and documentation language:** English

**Runtime:** Node.js 22.19+, TypeScript, Next.js App Router, local Chromium

**External service:** OpenRouter only, for explicitly authorized image and agent requests

**Persistence:** Gitignored local JSON files and images; no external database

This is an implementation plan, not a request to execute paid API calls. The deliberately small phases in Section 12 are separate coding-agent assignments. Complete and report one phase before starting the next.

## 1. Objective and Fixed Requirements

Build a local e-commerce demonstration in which OpenRouter generates product photographs and an AI agent uses a real local Chromium browser to explore the website and complete test forms. The application should make both the browser interaction and its independently evaluated outcome visible.

The following are non-negotiable:

- Exactly 24 source-controlled, deterministic products, with six products per unfiltered catalog page and four initial pages.
- Product attributes are fixed in source code; only images are generated by AI.
- A browser-based OpenRouter setup flow; no shell-based API key setup for ordinary users.
- Valid generated images survive refreshes and application restarts; missing images do not trigger automatic paid regeneration.
- One dedicated local Chromium session per agent run and at most one active agent run.
- Two working local test forms, five predefined browser tasks, deterministic evaluation, and persistent run history.
- One repository, one primary development command, and TypeScript for application code.
- Routine tests and builds use mocks and never make billable OpenRouter requests.

The local storefront remains browseable with placeholders while images are incomplete. Agent execution requires an available key and a verified compatible model, but browsing the catalog does not.

## 2. Scope and Technology

| Concern | Choice |
|---|---|
| Web application | Next.js App Router, React, Tailwind CSS |
| Language and validation | Strict TypeScript, Zod |
| Browser agent | `@browser_use/pi`, subject to the compatibility gates below |
| Browser | Local Chromium; visible by default, headless only for suitable smoke tests |
| AI requests | OpenRouter image API and a separately configured OpenRouter agent model |
| Storage | Local JSON, individual form records, generated images |
| Job execution | In-process image batch, separate Node.js child process for each agent run |
| Progress | Persisted snapshots plus Server-Sent Events (SSE) |
| Tests | Vitest and Playwright; separate, opt-in live AI smoke tests |
| Package management | npm with a lockfile; `tsx` available at runtime for the worker |

Do not add Docker, Python, cloud browsers, a database, Redis, an orchestration framework, MCP/A2A, payments, authentication, multi-user support, general-purpose scraping, or production deployment. Prefer direct, readable functions to unnecessary abstraction layers.

Use stable compatible package versions and the APIs of the versions actually installed. All routes touching files, secrets, processes, or the SDK must run in the Node.js runtime. Pages that inspect runtime files must render dynamically, rather than capture setup state during `next build`. Use local/system fonts and local assets, no external CDN or analytics, and set `NEXT_TELEMETRY_DISABLED=1` for Next commands: after installation, normal application traffic should leave the machine only for explicitly approved OpenRouter requests.

Enforce the minimum Node.js version, not just document it: set `package.json` `engines.node` to `>=22.19`, pin a compatible default in `.nvmrc`, and fail fast before `dev`/`start` on an older runtime. A project `.npmrc` with `engine-strict=true` can also fail installation early; the runtime check still covers launches that bypass npm's engine validation.

Target Linux or WSL for the documented, tested workflow. Visible Chromium needs a working graphical display (for example WSLg); a missing display or Chromium binary must produce installation guidance. Browser Use Pi expects an installed Chrome/Edge/Chromium (common Linux paths include `/usr/bin/google-chrome`, `/usr/bin/chromium`, and `/usr/bin/chromium-browser`) and permits an explicit `executablePath`; it does not supply a bundled browser. Playwright's test-browser installation is separate, so document and verify both.

```text
tests/

  .server.lock                     # One active local server per data directory
  settings.json                    # Model choices; never contains the key
  agent-compatibility.json         # Verified model/SDK/origin tuple, never the key
  secrets/openrouter-key           # Only when Remember API Key is enabled
  images/manifest.json
  images/P01-<attempt-id>.<format>  # Active file selected by manifest; through P24
  images/orphans/                  # Unmatched files preserved for inspection
  image-job.json                   # Current batch snapshot and stop request
  locks/paid-job.lock              # One paid operation at a time
  submissions/support/<uuid>.json
  submissions/inquiry/<uuid>.json
  agent-runs/<uuid>.json
  agent-events/<uuid>.jsonl
  browser-profiles/<run-id>/
```

- Missing `data/` or individual files are normal on first launch. Create them lazily on the server with restrictive permissions where supported.
- Keep `data/` out of `public/` and Git. Serve only allowlisted image IDs through a Node route, never arbitrary filesystem paths. Do not put keys, images, submissions, recordings, or profiles into a client bundle.
- Write JSON snapshots and image bytes through temporary files and atomic same-directory renames. Use exclusive creation or a single-writer lock where concurrent requests can otherwise overwrite state. Event `.jsonl` files are the deliberate exception: write bounded records with `O_APPEND`, never rewrite history, and tolerate/report a truncated final line after a crash. Treat malformed stored snapshots as an explicit recovery error, not as permission to discard user data.
- Store timestamps in UTC, use UUIDs for submissions and runs, and keep form records in separate files to avoid read-modify-write races.
- The image manifest is the authoritative lifetime ledger: for each product it records the currently published image pointer, validated format/size/hash when present, **and** attempts identified by UUID with start time, status, filename, and reported/estimated/unknown cost. Record a started attempt before calling the provider so replacing `image-job.json` for a later batch cannot erase earlier charges. The job file holds only the current batch's targets/status/progress and a persisted, job-ID-scoped stop request; derive totals from the manifest.
- Use a unique `P01-<attempt-id>.<format>` filename for each attempt. A regeneration must never overwrite its previously valid image: publish the new validated file, then switch the manifest's active pointer; keep the old file until the new pointer is durable. An image file, its manifest update, and its job snapshot cannot be committed in one atomic filesystem rename. Write and validate the image first, atomically update the manifest, then atomically update the job snapshot.
- After a crash between writes, reconcile an unpublished file **only** when its product/attempt ID matches a manifest attempt still marked `started`, its modification time is no earlier than the attempt start, and its format/content validate. Reconcile the already-paid result without making another request; its actual charge remains `unknown` if usage was not saved. Move any other unreferenced file to `data/images/orphans/` and report it instead of silently publishing or deleting it. Never infer a completed or unpaid request from a stale job snapshot.
- Each agent-run summary contains run ID, preset ID or custom task, selected model, start/end UTC times, execution status/SDK stop reason, step count, duration, bounded output, estimated or unknown usage/cost, evaluation and UI-evidence results, and (when the optional experiment exists) its UI mode captured **at start**. Store the worker PID while active for recovery, and store baseline form-submission IDs before launching a form-task worker. Persist a bounded, sanitized chronological event log separately. Show the newest 50 runs without automatically deleting older records.
- Enforce one local application server per data directory with `data/.server.lock`, acquired by the long-lived Node server at runtime, **not** by `next build`, pre-rendering, or each HMR-loaded module. A second server on the same data directory fails clearly; tests use separate data directories. Acquire `paid-job.lock` atomically **before** rechecking an image quote or spawning an agent worker; reject a competing start.
- On Linux/WSL, store `{ pid, procStartTicks, bootId, ownerId }` (plus an agent's process-group ID) in lock metadata. Read the boot ID and process start time from `/proc`; `ownerId` is the job/run ID or a server UUID. A PID alone is insufficient because it can be reused. Reclaim a stale lock only when that exact process identity is gone or changed; for an agent, also confirm the owned process group has no live descendants before releasing its paid lock. If ownership, group cleanup, or a competing recovery cannot be proved, fail closed and require manual inspection; never kill by PID alone or unlock by age. Apply the owner check to `.server.lock`. Mark interrupted work as interrupted and never resume a paid request on startup.

The image batch can continue after its initiating HTTP response while the local Node process lives. Keep the session-only key, image-batch controller, and agent-supervisor handle in process-wide `globalThis` holders keyed by `Symbol.for(...)` so module reloads do not start duplicate jobs or unnecessarily lose the key/worker handle; **disk state and the locks remain authoritative**, not those holders. A `next dev` process replacement can still lose them: show key unavailable, mark an interrupted batch/run appropriately, require key re-entry and a fresh quote for images, and never auto-resume a paid request. SSE readers reconnect from persisted snapshots, not a required in-memory registry. Agent work is supervised in a child process. Neither job relies on a browser tab remaining open.

Use `node --import tsx` (or an equivalently tested, single documented mechanism) to run `src/worker/agent-runner.ts` under both `npm run dev` and `npm run start`. Resolve its absolute path from the application repository root, **not** from a `.next` bundle directory, and fail clearly if it is absent. If using `tsx`, install it as a runtime dependency, not only a development dependency. Verify the worker also starts beside a built Next.js application; `next build` alone does not compile that standalone worker.

## 4. Secrets, Local Security, and Spending

### 4.1 API key lifecycle

- The setup form sends the key directly to a same-origin server endpoint. Never store it in localStorage, cookies, URLs, source files, client-side settings, browser bundles, telemetry, run events, or logs; never send it back to the client, even masked by returning its prefix.
- Validate credentials with `GET https://openrouter.ai/api/v1/key` and `Authorization: Bearer <key>` (recheck the current primary docs), a timeout, and a strict `200` response containing `data`; `401` is invalid credentials, while a network/5xx error is not. Do not forward/log its returned metadata or masked key label. A management-only key is not proof of inference access, and a successful validation does not prove model entitlement or sufficient image credits.
- Default **Remember API Key** to off. With it off, keep the key only in the local server process; refreshes may reuse it, but a server restart requires entry again. With it on, store it only in `data/secrets/openrouter-key` with a private directory and mode `0600` on Linux. Disclose that this is plaintext local storage, not encryption, and that WSL/other filesystems may not enforce equivalent permissions.
- Replacing a remembered key with a non-remembered one removes the old disk copy. Any key replacement, re-entry after losing a session-only key, or deletion invalidates the browser-model compatibility record **before** the new key can become active; abort the change if invalidation fails. Account/model entitlement may have changed. Allow replacement and deletion, but refuse either while a paid operation is active. Deleting the key does not delete valid product images: setup can remain image-complete while agent controls request a key.
- Pass a needed key to the agent child through a private process channel/environment, never through command-line arguments or event payloads. The agent SDK executes generated JavaScript outside a security sandbox; a child process and prompt restrictions do **not** make a hostile model or prompt safe from the key. Use only trusted local pages, tasks, and test data.
- Recommend a dedicated OpenRouter key with a low account-side spending limit and explain how to rotate it if exposed; local soft limits do not replace provider-side limits.

### 4.2 Local HTTP boundary

- Bind both development and built servers to `127.0.0.1` by default (Next CLI supports `-H 127.0.0.1 -p 3000`). Use one configured origin (default `http://127.0.0.1:3000`) for browser tasks and API requests. An `APP_ORIGIN` override may select only a loopback hostname/IP and explicit port; configure the server's bind host/port and Host guard consistently, rather than silently switching ports. Do not listen on the LAN by default. Provide a read-only `/api/health` returning `200` and a fixed application marker only from a server that holds `.server.lock`, never a secret.
- Protect **all** state-changing endpoints, especially key changes, generation, agent start/cancel, submission resets, and forms. Validate `Host` against the configured loopback origin and require an exact same-origin `Origin` for browser POST/DELETE requests (or a server-issued CSRF token when Origin is absent). Accept JSON with bounded size, validate it with Zod, and never enable permissive CORS. GET and SSE endpoints must not perform paid or destructive work.
- Whitelist IDs for image and run-file routes, avoid path traversal, set the actual image content type and `nosniff`, and do not render agent output as HTML. Local-only operation is not a substitute for authentication on an exposed server.
- For isolated E2E tests only, permit a **shared server-side** `OPENROUTER_BASE_URL` override for key validation, image-model/pricing lookup, and image generation with an explicit `LAB_TEST_MODE=1`, a loopback mock URL, a dummy key, and a temporary `DATA_DIR`; reject the override outside that mode rather than risking a real key being sent to another server. The browser SDK is mocked separately in deterministic tests. Never expose these controls through the user-facing setup form.

### 4.3 Paid operations

- Generation starts only after a user sees the **current** missing/selected images, verified per-image estimate, ordinary estimate, and worst-case estimate with up to two retries, then explicitly confirms. After acquiring the shared lock, the start endpoint recomputes that quote and rejects changed targets, model, or pricing before any paid request. Use decimal/fixed-point USD precision (the candidate unit price is below one cent); do not round each image before summing. Unknown pricing is not `$0`: choose a verifiably priced model or block the paid operation until a defensible estimate is available.
- A fresh retry or intentional regeneration requires a new confirmation. Never overwrite a valid image or reissue an uncertain interrupted request automatically. Report that a network timeout can still incur provider charges even when no response arrives.
- Agent runs show the selected model, configurable bounded step/time/soft-cost limits (defaults: 30 steps, 180 seconds, $1.00) before **Run Task** is clicked. Validate limits server-side; pass `maxCostUsd` to the verified SDK, which checks between turns and may overshoot by one response. If usage is unavailable, label cost/limit enforcement unavailable and warn before running; still enforce step/time limits. SDK usage is an **estimate**, not a provider invoice; do not report an unknown cost as zero or promise a hard billing cap.
- Browser SDK live smoke tests, image previews with a real model, and the optional experiment are billable operations too. They require explicit opt-in and are excluded from normal `test`, `test:e2e`, and `build` commands.

## 5. External API Compatibility Gates

The candidate model names and API examples have been checked against public documentation as of 2026-10-23, but public catalog entries do not prove that a particular account can use them. Recheck and record the selected model ID, installed SDK version/API, endpoint/parameters, response shape, and price source during implementation. Do not invent SDK options or silently switch providers or models.

### Images

- The documented image endpoint is `POST https://openrouter.ai/api/v1/images`. Read its **image-specific** catalog at `GET /api/v1/images/models` and the selected model's `/api/v1/images/models/{id}/endpoints` data for `supported_parameters`, formats, and per-resolution pricing. Do not use the general `/api/v1/models` catalog to infer image-model availability.
- The currently listed candidate `black-forest-labs/flux-3-image-klein` supports `resolution: "768"`, `aspect_ratio: "1:1"`, and `n: 1`; its public 768-tier example price on 2026-10-23 was $0.008/image (24 images about $0.192 before retries). This is **not** a pinned future price or proof of account entitlement. Check the actual provider endpoint/variant before quoting it in the wizard.
- Use one square image per request, sequentially; use the selected resolution only if supported. The documented image response has `data[0].b64_json`, `media_type`, and `usage.cost`; validate the response shape and do not infer format from the model/tier. Accept only deliberately supported raster formats; reject SVG unless a separate safe handling design is approved.
- Validate HTTP status and body, bound response size, decode the image, check a supported PNG/JPEG/WebP signature and plausible dimensions, and name the file by its returned/verified `media_type` and actual bytes. Reject unsupported/empty/corrupt responses before publishing a manifest success.
- The image API can return HTTP 402 when the available account balance is below **$1 before each request**, even if the projected batch costs less. To finish 24 successful requests at $0.008 each, an account starting at exactly $1 would run below that floor after the first request; roughly $1.184 is needed *before* the batch to still have $1 before request 24 (more with billable retries). Show this as an indicative starting-balance floor, not a provider invoice; stop on 402 and give actionable guidance. A public model listing does not prove that the key can pay for generation.
- Keep the provider-specific request/response logic in one small TypeScript adapter. A model change requires rechecking price and capabilities and a new user-approved quote, not rewriting the wizard.

### Browser agent

- The currently documented `@browser_use/pi` v0.1.0 API uses `Browser.chromium({ profileDir, headless: false })`, `BrowserUse.create({ model, browser, ... })`, `agent.run(task, { schema, maxSteps, timeoutMs, maxCostUsd, signal, onEvent, ... })`, and `agent.close()`. Set `headless: false` explicitly for the visible demo; local Chromium defaults to headless. Recheck the installed version and its TypeScript types rather than guessing event payloads or options.
- The documented initial OpenRouter model `openrouter/openai/gpt-5.6-luna` is the suggested initial choice, not proof of account access. Default the browser-model field to this ID; allow an advanced free-text ID only after bounded Zod format validation and a new compatibility check. Verify the selected model publicly advertises image/vision input for screenshot interpretation and succeeds in Phase 22. Pass the API key to the child via `OPENROUTER_API_KEY`, which the SDK expects; a public model-listing request is not a live inference check.
- Use hostname values (not full URLs) for the SDK's `allowedDomains`/`prohibitedDomains`; inspect their installed types and test local browser navigation to **both** `127.0.0.1` and `localhost` without inference. Confirm actual domain enforcement in an authorized agent smoke if it cannot be exercised through browser primitives; keep the supported choice consistent with the configured origin and Host guard. These controls restrict navigation, **not** arbitrary network access. Optional research and shell tools are opt-in: leave them disabled. Explicitly set `telemetry: false` and `highlightActions: true`, since the defaults do the opposite.
- Phase 0 establishes local Chromium feasibility without inference or a key. A later, separately authorized AI heading smoke tests actual account/model access before calling the integration *verified*. If no key or spending approval is available, downstream **mock-only implementation** may proceed but arbitrary live agent tasks stay disabled and the live gate stays `Unverified`; a demonstrated SDK incompatibility is `Blocked` and requires an explicit architecture decision before continuing dependent features. Evaluate Stagehand only after such a decision; do not quietly add a Python service or cloud browser.
- Persist `data/agent-compatibility.json` (model ID, installed SDK version, local origin, verification time, vision-evidence status; no key) only after a successful authorized smoke **using the app's current key**. Invalidate it before key/model changes and check the SDK version and origin tuple again on every start, so a crash between separate file writes cannot activate a stale stamp. A public model catalog entry alone never sets this record. A developer-only smoke can read the current remembered key and stamp the app, or use a temporary TTY key for SDK research **without stamping an unproven app account**; it must honor the shared paid lock. The ordinary user instead has a browser-based **Verify Agent Model** action using the wizard's server-side key, even with Remember off. This action runs only a fixed, short local heading task after a separate cost confirmation, not arbitrary instructions.
- A successful `/shop` heading smoke proves browser/model integration, **not** that screenshots reached the vision model. Record `vision: unverified` unless documented SDK events, usage, or request instrumentation actually establish image input; total token counts and a correct DOM answer do not. An optional, separately authorized visual-only smoke may upgrade it to `observed` when transport evidence exists. Display this distinction without blocking DOM-capable tasks or inventing image-token metrics.
- Use the documented domain restrictions, fix the starting URL to the configured loopback application, and instruct the model to navigate only the local UI. These are risk reductions, not filesystem/network isolation: Browser Use Pi executes generated JavaScript in an unsandboxed process. App code and assets should initiate no external requests except OpenRouter, but strict machine-wide egress isolation would require an OS network policy outside this PoC; do not claim task instructions or an SDK hostname allowlist enforce it.

## 7. Setup and Image Lifecycle

### 7.1 Setup state

Compute a fresh status from persisted files rather than trusting a `completed` flag. Keep **key availability**, **valid active image IDs**, and **job status** as separate fields. Status precedence is: live job `generating`/`stopping`; otherwise 24 valid active images `completed` (show a failed regeneration separately); otherwise any partial images or previous failed/interrupted/`stopped_by_user` attempt `incomplete`; otherwise missing key `not_configured`; otherwise `ready_to_generate`. A later key deletion does not undo valid images, and an incomplete state without a key asks for re-entry without deleting them.

Validate the manifest's **active** file for each product against its format, bounds, and stored hash. During regeneration keep the previous active success until the new pointer is durable. A valid unpublished file can be reconciled without a new paid request only under the matching started-attempt rule in Section 3; quarantine and report every other orphan. A missing/corrupt active image is incomplete. Preserve cost/attempt history even if an image is regenerated.

On a fresh launch, `/` directs the user into `/setup` (or displays the wizard entry) while `/shop` remains browseable with placeholders. The wizard presents welcome, key entry and non-billable validation, image-model/quote review, explicit batch confirmation, progress, and completion with a catalog link. It restores its view from saved state after refresh. Model configuration for browser inference is separate from the image model.

### 7.2 Image job

1. Prepare a server-side quote for missing or explicitly selected IDs; show the base estimate, three-attempt worst case, and indicative initial account balance needed to keep $1 available before **each** request. Generate an already valid image only on an explicitly chosen regeneration operation.
2. On the confirmed start, obtain the shared paid-operation lock **first**, revalidate the quote while locked, then persist `running` and the target list before issuing a billable request. If revalidation fails, release the lock without a paid call. Multiple tabs receive the same existing job/status, not a second batch.
3. For each target, record its attempt in the authoritative manifest, send one supported model request with a timeout, validate and atomically save the returned image, atomically update the manifest, and finally update the job snapshot. No cross-file transaction is implied: recover from any intermediate state on restart. Emit only sanitized progress and count each of the 24 successful IDs once.
4. Retry transient network/5xx/429 failures at most twice with capped exponential backoff and a bounded `Retry-After`. Do not retry 401/403, insufficient credits, unsupported model/parameters, or invalid image data automatically. Mark a failed item and allow the batch to continue when safe; stop the batch if authorization, billing, or model configuration is broken.
5. A same-origin **Stop batch** action atomically persists a stop request for the current job ID. The worker reads it between requests and before retries, preserves it across progress writes, and does **not** abort a request already in flight. Display `stopping` until that request settles, then persist `stopped_by_user` and release the lock. Duplicate/late stop actions are idempotent; continuing requires a new quote and confirmation.
6. On process death, reconstruct image validity and mark the previous job `interrupted`. No startup or page load makes a new paid call. **Retry Failed Images** or **Resume Missing Images** needs a fresh, current quote and confirmation; it reuses valid files and cannot silently replay an ambiguous in-flight request.
7. Mark the **job** completed only when every target succeeds or was deliberately reused, there is no stop/failure, **and** all 24 active files validate. A failed regeneration may leave 24 older valid images and thus image setup `completed`, but its job remains failed. Record reported cost where available and clearly labeled estimates/unknown billing otherwise, including attempts that may have been billed but returned no image.

SSE delivers a persisted state snapshot immediately and later progress updates, with no cache and clean disconnect handling. Reconnect/refresh must display current state, not require all past events in memory. A GET status fallback may poll if SSE is interrupted; neither GET endpoint starts work. The image route serves only validated IDs and the correct format, with safe caching or a versioned URL so a regenerated image is not displayed stale.

## 8. Local Test Forms

Both forms submit only to same-origin Node routes and use Zod server-side validation, visible field errors, UUID confirmation IDs, and persisted records with UTC creation time. Add practical input-length bounds and use escaped text in every view. There is no email, checkout, or payment integration.

| Route | Required fields and behavior |
|---|---|
| `/forms/support` | Full name, valid email, subject, priority (Low/Normal/High), description, and checked local-test confirmation. Review all values **before** final submission. Show a persisted request ID on confirmation. |
| `/forms/inquiry` | Full name, valid email, existing product ID, inquiry type (Availability/Specifications/Other), and message. Allow product preselection from its detail page. Show a persisted confirmation ID. |

Provide a simple local submissions view (at least inquiries; both types are useful for manual verification). ## 9. Browser Agent and Dashboard

### 9.1 Worker and supervisor

- A supervised Node.js child process performs **one** task and creates **one** dedicated Chromium browser/profile. The SDK also locks each `profileDir` against concurrent owners; never reuse a profile concurrently. Start at the configured loopback storefront, perform interactions through the real browser UI, and always close the browser in `finally` on success, error, timeout, and cancellation. Remove its disposable profile when safe; do not touch a user's regular browser profile.
- Pass the selected model, trusted task instruction, URL, limits, and key through private IPC/environment. Do not supply fixture contents, hidden expected results, filesystem tools, or internal API tools to the agent. Instructions forbid source/secret reads, shell use, purchases, external navigation, and direct API calls. The SDK's unsandboxed JavaScript means those instructions are **not** a security guarantee.
- Normalize SDK events/results into small validated IPC messages; redact credentials and sensitive headers and bound event/output size. The supervisor, not the model, records events and final status on disk. Do not claim a UI action was seen if the SDK provides no such event.
- Before **any** worker spawn, including Verify Agent Model, make a short, no-charge GET to the configured `/api/health` and require its `200` response and fixed app marker; a wrong port, stopped server, or unrelated service fails with an actionable error. Then acquire the shared paid lock **before** spawning the worker. Give each run a UUID. Provide start, status, events, and cancellation APIs. A second start is rejected; cancellation uses the SDK `AbortSignal`/`cancel()` and **awaits cleanup before another run**, then escalates a stuck worker after a short grace period. Enforce the configured wall-clock timeout even if SDK cancellation hangs. Pass validated `maxSteps`, `timeoutMs`, and `maxCostUsd` to the SDK; preserve its stop reason (`cancelled`, `cost_limit`, `timeout`, `max_steps`, etc.).
- On Linux/WSL spawn the worker with `detached: true` in its own process group and persist its PID, group ID, and process identity. Handle IPC `disconnect` inside the worker and use a bounded parent heartbeat/watchdog as a backup. On normal cancel first request SDK/browser shutdown; after grace, signal the **verified owned process group** (`SIGTERM`, then `SIGKILL`) so Chromium and SDK grandchildren are not left behind. Check process identity before any group signal to avoid PID reuse; test that descendants really exit, and report/manual-clean up if the SDK launches one outside that group. On worker crash or parent restart, mark an orphan run `interrupted`/`error` and preserve the trace. Never treat a saved `running` flag as proof of a live supervisor.

### 9.2 Dashboard

`/agent` offers a custom task field, a selector for five presets, validated step/time/soft-cost controls, model/vision-evidence and billing warnings, Run/Cancel controls, current status, step/latest action, chronological event trace, final output, independent evaluation result, and a recent-history view. Do not allow an **arbitrary live task** without a key or current browser-compatibility record for its selected model/SDK/origin; provide a separately confirmed, bounded browser-based **Verify Agent Model** smoke using the same server-side key. A reset control, if present, explicitly targets form test data and is disabled during runs.

Display reported model, steps, duration, input/output tokens **when exposed**, and SDK-estimated or unknown agent cost with the right label. Persist a monotonic sequence number with bounded events: SSE starts with a run snapshot and recent events, then emits new events; after reconnect/refresh, replay from disk or send a fresh bounded snapshot and deduplicate by sequence. Disable SSE caching and clean up disconnected readers. The visible Chromium window, interaction highlights, and trace are sufficient visualization. The SDK documents optional recording artifacts; export/display them only if supported and safely stored under `data/` (MP4/GIF export may need `ffmpeg`). Do not assume screenshot events exist or build video streaming/a second browser driver.

Keep execution status (`running`, `completed`, `limit_reached`, `error`, `timed_out`, `cancelled`, `interrupted`), SDK stop reason, business evaluation (`passed`, `failed`, `not_evaluated`), and UI evidence (`observed`, `unverified`) separate. A cost/step limit is not a completed business task. Custom tasks have no deterministic evaluator and remain `not_evaluated`, not automatically passed. If the optional UI experiment is enabled, record its mode at the **start** of each run and show it in history.

## 10. Predefined Tasks and Independent Evaluation

The agent receives a task instruction, a local site URL, and a neutral answer-format request, **not** expected values or direct access to catalog fixtures. The SDK documents `schema: Type.Object(...)` and `validateResult`; use these when compatible with the chosen model and independently validate the returned data with Zod on the server. Otherwise request small JSON output and parse it strictly. The neutral JSON shapes are `{name, priceUsd, url}` for Task 1, `{names, count}` for Task 2, `{items: [{name, priceUsd}]}` for Task 3, `{requestId}` for Task 4, and `{confirmationId}` for Task 5. Ambiguous, unparsable, or extra incorrect answers fail evaluation rather than being sent to an LLM judge.

1. **Cheapest available Home product.** Instruct: "Find the cheapest currently available product in the Home category. Return its exact name, USD price, and product page URL." Expect `Pebble Plant Pot`, USD 22, P19, and `/shop/products/pebble-plant-pot` at the configured local origin.
2. **Out of stock.** Instruct: "Inspect the catalog and return the names of all out-of-stock products and their total count." Expect exactly `Atlas Travel Backpack`, `Pulse Sport Earbuds`, `Glow Aroma Diffuser`, `Aero Laptop Stand`; count 4. With no out-of-stock-only control, this exercises multiple default pages.
3. **Audio comparison.** Instruct: "Find every in-stock Audio product priced below $70; return names and USD prices in ascending price order." Expect `Mini Bluetooth Radio` (44), `Echo Mini Speaker` (59), in that order. Filtering Audio fits six items on one page, so do **not** assert that this task necessarily paginates.
4. **Support request.** Instruct: "Using the support form, submit name Alex Demo, email alex@example.com, subject 'Payment confirmation issue', priority High, description 'I did not receive a confirmation after the simulated payment.' Review the details, check the local test submission confirmation, submit, and return the request ID." Expect exactly one **new support** record with all matching fields and its exact ID in the agent's answer.
5. **Product inquiry.** Instruct: "Find Clarity Webcam and use its inquiry form. Submit name Alex Demo, email alex@example.com, product Clarity Webcam, inquiry type Specifications, and the message 'Does this webcam support 1080p video recording?'. Return the confirmation ID." Expect exactly one **new inquiry** record with matching P22, other fields, and confirmation ID in the answer.

The evaluator computes product expectations from the fixed fixture but tests also assert the literal expected items above. Normalize only insignificant JSON/whitespace/case differences; compare complete sets (not substrings), counts, numeric USD prices, and sort order exactly. Resolve a relative Task 1 URL against the configured origin and normalize an optional trailing path slash, then require that its **origin, including port**, and product-detail path match P19. Do not automatically equate `localhost` with `127.0.0.1`: only an explicitly configured, verified origin alias could be accepted. Reject external origins or extra incorrect names.

Before a form-task run, snapshot existing submission IDs. Require **exactly one** new record of that form type, with every prescribed field (including the support checkbox or inquiry type/message) correct; the returned UUID must identify that record. An old matching record cannot satisfy the run; a duplicate submit or concurrent manual submit makes it fail and can be retried in a separate run. Do not clear historical submissions automatically. Store the result once at run termination, not by rescanning after a reset.

Require a documented browser-action trace for a predefined task to be labeled fully passed: catalog tasks must show local shop browsing, and form tasks must show the relevant form page and UI interaction where the SDK exposes those events. Overall success requires a `completed` execution, a `passed` business evaluation, and `observed` UI evidence. Do not add a product-read JSON API just for the agent; render the catalog server-side. If the installed SDK cannot provide adequate UI evidence, show the business-result evaluation separately as **UI use unverified** rather than claiming a proven browser-only pass. A trace is useful evidence, not cryptographic proof against an unsandboxed agent calling internal APIs directly.

## 14. Core Definition of Done

A user can clone the repository with Node.js 22.19+, run `npm install && npm run dev`, open `http://127.0.0.1:3000`, enter a key through the wizard, review and confirm a defensible image-generation quote, and watch 24 images appear without duplicates. After restart, the catalog still displays four six-item default pages, usable filters/detail views, and saved images without further billable generation. Deterministic suites pass without a provider account. Live image and agent validation requires separate authorization and must be reported as unverified, not complete, until actually observed.
